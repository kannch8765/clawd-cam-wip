# ClawdCam 0.2.0 Feature Reference and Adoption Survey

Status: Task 009 documentation-only survey  
Frozen ClawdCam base: `ba5c755ecbd91cdf020efcbefddfe8e8f21c195f`  
Survey date: 2026-08-06

## Scope and decision rule

This survey covers camera framing/zoom, photo filters, and one custom uploaded sticker. It does not authorize implementation. The governing constraint is to preserve the stable ClawdCam camera, overlay, composition, gallery, and sharing boundaries rather than replacing them with a general camera or image editor.

Decision terms:

- **ADOPT**: use the platform primitive or existing ClawdCam boundary directly.
- **ADAPT**: borrow a narrowly scoped behavior or data model behind a ClawdCam-owned interface.
- **REJECT**: do not add the candidate because it duplicates or destabilizes existing architecture.
- **DEFER**: valid later work, but outside the first implementation slice.

## A. Camera zoom and focal presets

### Platform behavior

A video track exposes hardware zoom only when all of the following are true:

1. the selected camera/source supports zoom;
2. the user agent exposes that source property through `MediaStreamTrack.getCapabilities()`;
3. the returned capabilities object contains a usable numeric `zoom` range;
4. the active track accepts a corresponding constraint through `applyConstraints()`.

The property is optional. Its absence is normal and must not be treated as a camera error. The Image Capture specification defines zoom-related constrainable properties, but ClawdCam does not need `ImageCapture.takePhoto()` for its existing Canvas composition pipeline.

After every camera start or front/rear switch, ClawdCam must read capabilities and settings again from the new active video track. Capabilities and current settings belong to a particular track/source; retaining the previous camera's range or applied value is invalid.

`applyConstraints()` is asynchronous and can reject, commonly with `OverconstrainedError`, or fail because the track ended or the source changed. Correct recoverable behavior is:

- keep the camera stream usable;
- preserve or re-read the last confirmed `getSettings().zoom` value;
- return the UI to the nearest valid preset/state;
- show a non-blocking recoverable message;
- never restart the whole camera automatically unless the track itself became invalid;
- ignore stale completion from a superseded request or camera session.

The Media Capture specification states that failed constraint application leaves existing constraints in effect. Implementation must still re-read settings because the product should display confirmed state, not an optimistic requested value.

### iOS Safari and installed-PWA boundary

General `getCapabilities()` support is now broadly documented, but the presence and behavior of `MediaTrackCapabilities.zoom` on iPhone cameras, including installed-PWA execution, depends on WebKit, device hardware, selected lens and OS version. This survey found no ClawdCam-owned physical-device evidence proving reliable hardware zoom across the supported iPhone lane. Therefore:

- iOS Safari hardware zoom: **unproven**;
- installed-PWA hardware zoom: **unproven**;
- hardware zoom must be an optional enhancement, never the baseline for the focal-preset feature.

Task 010 device tests should record capability objects and confirmed settings without assuming that browser support implies camera support.

### Universal digital framing baseline

Digital framing should be implemented with ClawdCam-owned crop geometry, not CSS-only scaling and not screenshotting the preview DOM.

Define one camera-framing state separate from `OverlayTransform`, for example:

```ts
interface CameraFraming {
  presetId: FocalPresetId;
  zoomRatio: number;
  centerX: number;
  centerY: number;
}
```

For the first version, `centerX` and `centerY` remain fixed at `0.5`; movable crop center is **DEFERRED**. Given the base cover crop already calculated for the preview aspect ratio, digital zoom divides the visible source width and height by `zoomRatio`, then centers the reduced source rectangle inside the base crop. Preview rendering and JPEG composition must consume the same geometry function.

At shutter time, `freezeCaptureSnapshot()` must freeze:

- active camera source identity and source dimensions;
- preview dimensions;
- selected framing preset and effective digital zoom ratio;
- final source crop rectangle;
- output dimensions;
- overlay asset and transform;
- filter preset ID when filters exist.

The export must draw the camera using that frozen crop. It must not recompute from current UI state after asynchronous image decode or blob encoding begins.

### Focal preset model

`24 / 35 / 50 / 77 / 120` must be presented as **equivalent framing presets**, not claimed physical focal lengths. A browser normally cannot prove the physical focal length, sensor crop, lens switch or optical/digital path used by the camera implementation.

Use 24-equivalent framing as the widest product baseline and derive relative crop ratios:

```text
24 -> 1.0000x
35 -> 35 / 24 = 1.4583x
50 -> 50 / 24 = 2.0833x
77 -> 77 / 24 = 3.2083x
120 -> 120 / 24 = 5.0000x
```

The UI label should say, for example, `35 eq.` or explain once that the values describe framing. A preset may be disabled when the source resolution would make the crop too small for the minimum export-quality policy.

If hardware zoom exists, ClawdCam may apply a bounded portion of the requested ratio in hardware and use digital crop for the remainder. The resulting preview/export geometry must still be expressed in one effective framing model and verified from confirmed settings. No preset may depend solely on hardware zoom.

### Gesture decision

Camera pinch-to-zoom is **REJECTED for the first version**. ClawdCam already assigns pinch to sticker scale/rotation; adding a competing camera pinch target creates ambiguous ownership and lifecycle races. Task 010 should provide discrete preset controls only. A later gesture task could introduce explicit mode or hit-target arbitration, but should not overload the existing sticker gesture surface implicitly.

### Zoom recommendation

**ADOPT** a universal digital framing baseline using native video + Canvas source crop.  
**ADAPT** capability-detected track zoom from the WebRTC PTZ sample and official constrainable-pattern APIs.  
**REJECT** replacing ClawdCam camera lifecycle with `react-camera-pro` or `react-webcam`.

Recommended architecture:

```text
universal digital framing baseline
+
capability-detected hardware zoom enhancement
```

## B. Photo filter pipeline

### Shared preset definition

CSS preview filters and Canvas 2D export filters accept substantially similar filter-function strings. ClawdCam can define presets as pure data:

```ts
interface FilterPreset {
  id: string;
  label: string;
  cssFilter: string;
  canvasFilter: string;
}
```

For presets limited to functions shared by CSS and Canvas, both strings may initially be identical. Keeping separate fields avoids pretending rendering is guaranteed pixel-identical and leaves room for per-engine adjustment.

The live preview applies `cssFilter` only to the camera video element. The overlay remains outside that filtered element. During export:

1. `context.save()`;
2. set `context.filter = preset.canvasFilter`;
3. draw the camera source crop;
4. `context.restore()` or explicitly set `context.filter = 'none'`;
5. draw the sticker in original color.

This makes the product rule explicit: filters affect camera pixels, not camera plus sticker.

### Visual and browser limits

CSS and Canvas filters can differ because of color-management, interpolation, filter implementation, backing resolution and browser engine behavior. The preview is an approximation of the final image, not a byte- or pixel-identical proof.

MDN marks `CanvasRenderingContext2D.filter` as limited availability rather than Baseline. Browser support and practical behavior on the ClawdCam iOS installed-PWA lane are therefore **unproven until device validation**.

Fallback policy:

- feature-detect that the 2D context has a usable `filter` property;
- if unavailable, expose only the `none` preset or disable filter selection with an explanatory message;
- if export setting/drawing fails, capture without a filter only after explicit product policy and UI feedback; do not silently save a visually different photo while still showing the selected filter;
- keep the rest of capture, gallery and sharing operational.

Task 011 should validate each supported preset on installed iPhone PWA and compare preview against exported output sufficiently to catch gross mismatch, not demand pixel equality.

### Dependency comparison

#### Native CSS + Canvas 2D — ADOPT

This fits the existing pipeline exactly: React owns live preview, and `composePhoto()` owns final rasterization. It requires only a small preset table, a camera-preview style and a frozen snapshot field. No scene graph or second renderer is needed.

#### Lightweight filter utility — ADAPT only if evidence demands it

A small pure utility that produces filter strings or matrices could be considered only if native preset definitions become repetitive. It must not own capture state, canvas lifetime, layers or image loading. No reviewed dependency provided enough value to justify installation in Task 011.

#### Full image editor — REJECT

Filerobot, Fabric, Pixi/Konva-based editor systems are designed for crop/rotate, layers, annotations, object selection, history, serialization or post-capture editing. Introducing one would duplicate the stable overlay controller and Canvas exporter, enlarge the dependency and UI surface, and pressure ClawdCam toward a general editor.

The first filter task must prohibit post-capture nondestructive editing, undo/redo, layer editing and a crop editor. `filterPresetId` belongs in the shutter-time `CaptureSnapshot`; gallery and sharing continue to receive one final `Blob`.

## C. Custom sticker upload

### First-version accepted formats

Recommended allowlist:

- `image/png` — ADOPT; primary transparent-sticker format.
- `image/webp` — ADOPT where decode succeeds; supports transparency and compact files.
- `image/jpeg` — ADOPT for user convenience, with no transparency expectation.
- animated `image/gif` — REJECT for Task 012A. Animation frame selection is nondeterministic for capture and complicates preview/export parity.
- `image/svg+xml` — REJECT for Task 012A. Safe SVG handling requires sanitization, external-resource restrictions and a tested rasterization boundary; MIME checking alone is not sufficient.

The file input should use an `accept` hint for the allowlist, but validation must inspect the actual `File.type` and successful image decode. Client-provided names and MIME values are not trusted proof of image safety.

### Decode and orientation

Prefer a ClawdCam-owned decode adapter:

1. validate file byte size and declared type;
2. create a short-lived object URL;
3. attempt `createImageBitmap(file, { imageOrientation: 'from-image' })` where supported and validated;
4. fall back to `HTMLImageElement` with `src = objectUrl` followed by `decode()`;
5. read decoded intrinsic dimensions before accepting the asset.

`createImageBitmap()` is useful for off-main-thread-capable decode and orientation options, but support and option behavior vary. `HTMLImageElement.decode()` is the compatibility fallback. JPEG EXIF orientation must be verified with fixtures; if neither path yields normalized orientation on a target browser, Task 012A must rasterize through an orientation-aware adapter or reject that file with a recoverable message rather than saving rotated content.

No small upload package removes the need for ClawdCam-specific limits, stale-session handling and mapping into `OverlayAssetDescriptor`. Native File/Blob/image APIs are sufficient for the first task.

### Resource limits

Exact constants belong to Task 012A tests, but the validation policy must bound all of these independently:

- compressed file size, with a conservative mobile limit;
- intrinsic width and height;
- decoded pixel count (`width * height`) to prevent decompression bombs;
- extreme aspect ratio;
- zero or non-finite dimensions;
- decode timeout and decode failure.

A reasonable implementation starting point for validation, subject to device testing, is 10 MiB compressed, 8192 pixels on either axis, 32 megapixels decoded and a maximum 20:1 aspect ratio. These are proposed guardrails, not browser guarantees.

### Object URL and stale lifecycle

Create an object URL only after initial file/type/size validation. Revoke it exactly once when:

- decode fails or times out;
- the candidate is superseded by a new selection;
- the component/session unmounts;
- a decoded object no longer needs the URL;
- an accepted temporary sticker is replaced or discarded.

Use monotonically increasing load-session IDs, the same pattern already used by `usePhotoCapture` for asset/capture sessions. A late decode from an old selection must dispose its resources and must not overwrite the current descriptor.

During capture, the shutter snapshot freezes the selected uploaded asset descriptor and decoded image/source identity. Replacing the UI sticker while capture is in progress must not alter the in-flight photo. The old resource cannot be revoked until the capture session no longer owns it.

### Mapping into the existing overlay boundary

An uploaded image should become an `OverlayAssetDescriptor`, not a new composition branch. Future type extension may add an asset origin and lifecycle handle, for example:

```ts
interface OverlayAssetDescriptor {
  id: string;
  version: string;
  previewSource: string;
  captureSource: string;
  intrinsicWidth: number;
  intrinsicHeight: number;
  anchorX: number;
  anchorY: number;
  origin: "bundled" | "uploaded";
}
```

The exact current field names should be extended minimally rather than replaced. For a static uploaded PNG/WebP/JPEG, preview and capture can refer to the same decoded asset. Existing drag, pinch, rotation, normalized transform geometry and Canvas overlay draw order should be reused unchanged.

### Persistence decision

Task 012A should be **upload and use now** only. A permanent local sticker library is a separate product and lifecycle concern:

- **Task 012A**: choose one file, validate/decode, map to overlay descriptor, use it for preview and capture.
- **Task 012B**: only if justified after 012A, persist validated source Blob plus metadata and thumbnails.

If Task 012B proceeds, it may reuse the existing IndexedDB connection/versioning approach, but sticker assets must live in a separate object store/repository boundary from gallery photo records. Gallery deletion, retention and schema assumptions must never control sticker assets.

Full editor asset systems and uploader dependencies are **REJECTED**. Native `<input type="file">`, File, Blob, object URLs and image decode primitives provide the needed first-version capability.

## D. Fit with current ClawdCam boundaries

The following findings are based on the frozen source tree.

### Camera

`src/features/camera/useCameraBase.ts` already owns bounded startup, request identity, stale-stream disposal, track-ended recovery, facing-mode restarts and the current `CameraCaptureSource`. Task 010 should extend the active-track adapter/state with capability/settings reads and recoverable constraint application. Zoom state must remain separate from sticker scale.

`src/features/camera/stageGeometry.ts` and the camera preview stage are the appropriate home for shared visible framing geometry. Hardware capability data must not leak into overlay types.

### Composition

`src/features/composition/compositionTypes.ts` defines `CaptureCropGeometry`, `CaptureSnapshot`, `CaptureSnapshotInput` and the output result. `CaptureSnapshot` already freezes camera identity, source dimensions, preview dimensions, crop, output, mirror policy, overlay asset/transform and timestamp.

Future minimal extensions:

- camera framing/preset metadata and effective crop geometry for Task 010;
- `filterPresetId` and resolved Canvas filter string for Task 011;
- no gallery- or sharing-specific feature branches.

`src/features/composition/usePhotoCapture.ts` already has asset load session and capture session ownership. Uploaded assets should plug into that lifecycle rather than bypass it.

`src/features/composition/composePhoto.ts` and `captureGeometry.ts` remain the sole final rasterization/geometry path. Camera filtering is applied only around the camera draw, reset to `none`, then the overlay is drawn.

### Overlay

`src/features/overlay/overlayTypes.ts`, `overlayAssets.ts`, `overlayGeometry.ts`, `useOverlayController.ts` and `useOverlayGestures.ts` already provide the correct single-overlay abstraction. Upload expands the asset descriptor/source, not the gesture or transform model.

Camera framing cannot reuse `OverlayTransform.scale`; they describe different spaces and lifecycles. Camera preset controls should not attach to the overlay pinch recognizer.

### Gallery and sharing

`src/features/gallery/` persists final photo and thumbnail blobs behind its repository boundary. `src/features/sharing/` consumes the same completed photo blob. Zoom, filters and custom sticker upload must be fully resolved before the `PhotoCaptureResult` enters either boundary.

No new gallery schema branch is needed merely because a photo used zoom, a filter or an uploaded sticker. Optional capture metadata can be added only through a deliberate schema migration. Sharing must never recompute or re-render a feature-specific photo.

### Candidates that would force rewrites

Adding a full camera component would duplicate `useCamera` request/session ownership and device-validation behavior. Adding a retained-mode or full image editor would duplicate overlay state, rendering order, capture geometry and mobile UI. Adding an asset-management uploader would blur temporary upload and persistent sticker-library boundaries. All are rejected for the planned 0.2.0 slices.

## Recommended implementation sequence

1. **Task 010 — Camera Zoom & Focal Presets**  
   Implement shared digital framing geometry and discrete equivalent-framing presets first; add capability-detected hardware zoom as a recoverable enhancement. Freeze framing into the capture snapshot and validate front/rear switching plus stale constraints.
2. **Task 011 — Photo Filter Pipeline**  
   Add a small declarative preset table, video-only CSS preview, camera-only Canvas filter draw and explicit unsupported fallback. Freeze filter ID at shutter time.
3. **Task 012A — Custom Sticker Upload**  
   Add native static PNG/WebP/JPEG selection, limits, decode/orientation handling, resource ownership and mapping to the current overlay descriptor/controller.
4. **Task 012B — Local Sticker Library** — conditional  
   Create only if product use after 012A justifies persistence. Use a separate IndexedDB store/repository from gallery records.
5. **Task 013 — Camera-first UI Redesign**  
   Redesign controls only after the feature states and unsupported/recoverable paths are known. Do not make UI work define architecture prematurely.
6. **Task 014 — Device Validation & Release Readiness**  
   Validate installed-PWA camera switching, digital framing parity, actual hardware-zoom exposure, Canvas filter behavior, upload limits/orientation and final Blob gallery/share flow.
